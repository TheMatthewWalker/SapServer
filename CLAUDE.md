# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build, Publish & Run

```bash
dotnet build
```

This is a **.NET Framework 4.8** ASP.NET Web API 2 application hosted via OWIN — there is no `dotnet run` self-host the way there was under ASP.NET Core; run it locally via IIS Express (Visual Studio / `dotnet iisexpress`) or a full local IIS site pointed at the build output. Swagger UI (Swashbuckle for Web API 2) is available at `/swagger` once wired up on a real IIS instance — see "Still to validate" below, since Swagger's `SwaggerConfig.cs` normally gets generated by the NuGet package's own install-time content, which only runs on a real `nuget install`/Visual Studio flow, not this sandbox.

Production is published **framework-dependent** (not self-contained — .NET Framework 4.8 ships with Windows Server, unlike .NET Core's optional self-contained publish) and deployed to an **IIS site + application pool**, not a Task Scheduler task:

```powershell
dotnet publish SapServer.csproj -c Release -o publish
```

`scripts/deploy.ps1` does this end-to-end (stop app pool → publish → start app pool → tail today's log). Other scripts: `install.ps1` (creates the `SapServer` IIS app pool + site, sets the `ASPNETCORE_ENVIRONMENT` machine env var, first-time setup), `start.ps1` / `stop.ps1` / `status.ps1` / `uninstall.ps1` (all IIS-cmdlet-based now — `Import-Module WebAdministration`), `watch-log.ps1` / `install-log-watcher.ps1` (unchanged — just tail `publish/logs`, independent of hosting model).

**This is a from-scratch .NET Framework 4.8 + SAP NCo rebuild of what was previously an ASP.NET Core 10 + SAPFunctions64-COM application** — see "Migration Notes" at the bottom of this file for why, and for what remains unverified. The COM/STA-thread-pool architecture, `Program.cs`, and Task-Scheduler deploy model described in any older notes no longer apply.

## Testing

```bash
dotnet build SapServer.Tests/SapServer.Tests.csproj
```

`SapServer.Tests` (xUnit + Moq + `Microsoft.Owin.Testing`), referenced from `SapServer.sln`. `[assembly: InternalsVisibleTo("SapServer.Tests")]` in `SapServer.csproj` lets tests reach the `internal` `Helpers/*` classes directly — no `Program`-partial-class trick needed anymore (that was specific to ASP.NET Core's top-level-statements + `WebApplicationFactory<Program>`; this project has no `Program.cs`, `Startup.cs` is the composition root instead).

**net48's older BCL is missing several .NET Core-only conveniences this codebase's `Helpers/*`/`Controllers/*` used throughout** — worth knowing before adding new code:
- `KeyValuePair<K,V>.Deconstruct` and `IReadOnlyDictionary<K,V>.GetValueOrDefault` — polyfilled via extension methods in `Net48Polyfills.cs` (both the main project and `SapServer.Tests` have their own copy — `global using` directives don't flow across project references, see each project's `GlobalUsings.cs`), so existing call sites needed no changes.
- `Math.Clamp`, `Task.IsCompletedSuccessfully`, `Dictionary<K,V>.TryAdd`, `System.Range`/`System.Index` slicing (`x[a..b]`, `x[^1]`), `DateOnly`/`TimeOnly`, `System.Globalization.ISOWeek`, `HttpStatusCode.UnprocessableEntity` (422) — none of these can be extension-method-polyfilled cleanly (can't extend a static class, no extension-property syntax, or the compiler needs real BCL type support for the language feature itself), so every call site was rewritten directly: `Substring`/manual indexing instead of range syntax, `DateTime` instead of `DateOnly`, a manual ISO-8601 week algorithm (`SalesHelpers.WeekNumber`) instead of `ISOWeek`, `(HttpStatusCode)422` instead of the named enum member. Grep for `net48 lacks` to find every one of these fix-up comments.
- `System.Web.Http.ApiController`'s `BadRequest(object)`/`NotFound(object)` don't exist (only parameterless/`ModelStateDictionary` overloads) — every controller uses `Content(HttpStatusCode.BadRequest, x)` / `Content(HttpStatusCode.NotFound, x)` / `Content((HttpStatusCode)422, x)` instead.

## Critical Platform Constraints

**Build x64, not x86, and target net48, not netcoreapp.** `SapServer.csproj` sets `<TargetFramework>net48</TargetFramework>` and `<PlatformTarget>x64</PlatformTarget>` (needed for the SAP NCo native binaries, which are x64-only) via the modern SDK-style project format (`<Project Sdk="Microsoft.NET.Sdk">`), not the classic Visual-Studio-generated non-SDK `.csproj` — this is deliberate: it's the only way `dotnet build`/`dotnet restore` work at all outside a Windows+Visual-Studio machine (see "Migration Notes"), and it's what let this rebuild be validated (compile-only) in a Linux sandbox.

**Deploy via IIS, not Task Scheduler.** The previous COM-based app needed Task Scheduler specifically because the SAPFunctions64 OCX required an interactive Windows session (IIS app pools run in Session 0, which caused `AccessViolationException` for that COM object). SAP NCo is not COM and has no such constraint — this app now runs as an ordinary IIS-hosted ASP.NET application (`scripts/install.ps1` creates the app pool + site; see Build/Publish/Run above). **Unverified**: this hosting decision has not been exercised against a real IIS instance from this sandbox (no Windows available) — validate the whole OWIN/`Microsoft.Owin.Host.SystemWeb` pipeline (auth, CORS, routing, `web.config`) on a real IIS site before trusting it in production.

**Secrets live directly in the config file, not machine environment variables.** `Auth:JwtSecret` (shared with sql2005-bridge) and `SapNco:ServiceAccount`/`ServiceAccounts` (SAP service account credentials — one or several, see "SAP NCo Connection Pool" below) are both filled in directly in `appsettings.Production.json`. That file is `.gitignore`'d the same as `appsettings.json`, and a plain config file is far easier to maintain than machine env vars. `install.ps1` only sets `ASPNETCORE_ENVIRONMENT` as a machine env var (unavoidable — `Startup.BuildConfiguration()` reads it to pick which `appsettings.{Environment}.json` layers on top of `appsettings.json`, so there's no config-file equivalent for it, and IIS app pool worker processes need a recycle to pick up a changed value). `appsettings.example.json` has placeholder values for both.

## Architecture

SapServer is a .NET Framework 4.8 ASP.NET Web API 2 (OWIN-hosted-in-IIS) REST API that wraps the **SAP .NET Connector (NCo)** to expose RFC/BAPI calls as authenticated JSON endpoints, replacing an older per-desktop WinUI 3 app (`sap-gui-async`) — and, as of this rebuild, replacing an intermediate ASP.NET Core 10 + SAPFunctions64-COM version of this same service (see "Migration Notes").

### SAP NCo Connection Pool — stateless pool + ephemeral pinned sessions

`NcoConnectionPool` (singleton, `Services/Nco/NcoConnectionPool.cs`, implements `ISapConnectionPool`) has **two independent execution paths**, sized and scaled completely differently — this is a deliberate correction over this rebuild's first pass, which carried the old COM-era "N dedicated STA threads, always alive" shape over into NCo almost unchanged even though NCo needs no thread pinning for ordinary calls (see "Migration Notes" below for why that mattered in practice, not just in theory):

- **Stateless pool** (`NcoStatelessPool`, backs `ExecuteAsync` — every ordinary, non-transactional RFC call, the large majority of traffic) — one NCo destination per configured `SapNco:ServiceAccounts` entry (or a single one for the plain `SapNco:ServiceAccount` when that list is empty), registered once at startup with **no dedicated thread at all**. `SapNco:PoolSize`/`MaxPoolSize` (default 10/20) configure *NCo's own internal connection pool* for each destination directly — NCo's pool is already thread-safe, so `CreateFunction`/`Invoke` on a destination leases and returns a physical connection internally per call, and any number of callers can run concurrently (via `Task.Run`) bounded only by that pool size, not by a .NET thread count. A connection failure here (`SapConnectionException`) gets one immediate retry (`SapNco:ReconnectDelayMs` backoff) before propagating.
- **Pinned sessions** (`NcoWorker`, backs `AcquireWorkerAsync`/`AcquireElevatedWorkerAsync` + `ExecuteOnWorkerAsync`) — for the one case that genuinely needs a dedicated thread: a stateful multi-call sequence (a create-BAPI followed by `BAPI_TRANSACTION_COMMIT`/`ROLLBACK`) that must land on the same SAP session's LUW. `RfcSessionManager.BeginContext(destination)` pins the *calling thread* to one physical connection — a SAP-level requirement independent of COM vs NCo. `AcquireWorkerAsync`/`AcquireElevatedWorkerAsync` construct a **fresh, single-use `NcoWorker` on demand** (its own thread, connects immediately, `BeginContext` once), bounded by a semaphore (`SapNco:MaxConcurrentPinnedSessions` / `ElevatedWorkerCount`, default 4 / 2 — queues up to `PinnedAcquireTimeoutSeconds`/`ElevatedAcquireTimeoutSeconds`, then throws `PoolExhaustedException`); the caller **must** call `ReleaseWorkerAsync`/`ReleaseElevatedWorkerAsync` in a `finally` block, which `EndContext`s and tears the thread down. Elevated sessions additionally connect with one specific user's own SAP credentials instead of the shared service account — this ephemeral, single-use lifetime is what stops one user's elevated session ever being reused for another user. No auto-reconnect on either kind: a pinned sequence that loses its connection mid-way can't safely resume a pending, uncommitted LUW, so the first failure just kills that session (the caller's own commit/rollback try/finally is what reports it back).

**This specific mechanism (`RfcSessionManager.BeginContext`/`EndContext`) is the single highest-risk unverified piece of this entire rebuild** — it's documented SAP NCo API, not something exercisable in this sandbox (no live SAP, no real NCo DLLs); validate a real create+commit sequence against a live system before trusting *any* transactional/elevated endpoint (PO creation, goods receipt, stock adjustments, packaging creation, freight posting) in production.

Total .NET threads at any moment = however many pinned/elevated sessions are *currently in active use* (0 at idle, up to `MaxConcurrentPinnedSessions + ElevatedWorkerCount` under load) — there is no fixed thread count started at app boot the way the COM-era design (and this rebuild's own first pass) had. Size `PoolSize`/`MaxPoolSize` and the pinned/elevated concurrency caps relative to your SAP system's concurrent-user license count, not CPU count.

### RFC Execution (`NcoRfcExecutor.Execute`)

Shared by both the stateless pool and pinned sessions — the NCo call pattern itself doesn't differ between them, only how the `RfcDestination` was obtained and which thread runs it:
- `destination.Repository.CreateFunction(name)` → `IRfcFunction`
- Import params: `func.SetValue(key, value)`; structures: `func.GetStructure(name).SetValue(field, value)`
- Input tables: `func.GetTable(name)` — `.Clear()` then `.Append()` per row (NCo has no COM-OCX-era `Tables`/`Tables.Item` split; both `RfcRequest.InputTables`/`InputTablesItems` map to the same `GetTable(name)`)
- The call itself: `func.Invoke(destination)`
- Output tables: `func.GetTable(name)`, iterate rows via the table's indexer

`RfcCommunicationException`/`RfcAbapRuntimeException` both map to `SapConnectionException` (503 `SAP_UNAVAILABLE`) — the stateless pool retries this once, a pinned session does not (see above). A genuine business-level ABAP exception (`RfcAbapBaseException`, e.g. `RAISE EXCEPTION` in the function module) maps to `SapExecutionException` instead (422 `RFC_ERROR`) and propagates straight to the caller — no retry, since the connection itself is fine.

**COM marshal / GC**: not applicable to NCo — it isn't a COM component. `IRfcFunction`/`IRfcTable`/`IRfcStructure` are plain managed objects, eligible for ordinary GC once they go out of scope; there's no `Marshal.ReleaseComObject` or `SAPFunctions64.RemoveAll()`-style leaked-registry cleanup needed — this is also why pinned/elevated sessions can be torn down and rebuilt per request cheaply, unlike the old COM path where a long-lived STA thread doing sustained `dynamic` COM interop was the actual source of the production out-of-memory crashes that motivated this NCo migration in the first place.

### JsonElement Unwrapping

ASP.NET (via `System.Text.Json`) deserializes `object?` parameters as `JsonElement`. `NcoRfcExecutor.Unwrap` converts these to CLR primitives (string, long/double, bool, null) before passing to NCo's `SetValue` — otherwise NCo rejects the value. `decimal` is coerced to `double` first (mirrors the old COM VARIANT limitation, kept for consistency even though NCo itself may not require it).

### Controllers — one generic + many domain-specific

`RfcController` (`api/rfc/execute`, `api/rfc/status`) is the original generic surface: caller supplies the raw RFC function name, import parameters, and which export parameters/output tables to read back. It still exists, but most functionality now lives in **typed domain controllers**, all deriving from `SapControllerBase` (which supplies `_pool`, `_permissions`, `_logger`, `GetUserId()`, and `CheckPermissionAsync(userId, functionCode, ct)`). Controllers are `System.Web.Http.ApiController`-derived (Web API 2), not ASP.NET Core's `ControllerBase` — `[RoutePrefix("api/x")]` at class level + `[HttpGet]`/`[HttpPost]` + `[Route("y")]` on actions (Web API 2's verb attributes don't support ASP.NET Core's inline-template constructor overload — `[HttpGet("y")]` — so template and verb are always two separate attributes here), `[FromUri]` instead of `[FromQuery]`, `IHttpActionResult` instead of `IActionResult`.

### Authentication & Permissions

JWT Bearer tokens are issued by a separate `sql2005-bridge`/Normanton-Nexus service (shared HMAC-SHA256 secret, claim `userId`), validated by Katana's `Microsoft.Owin.Security.Jwt` middleware (`app.UseJwtBearerAuthentication(...)` in `Startup.cs`) — the OWIN equivalent of ASP.NET Core's `AddJwtBearer`. The key-provider abstraction is `IIssuerSecurityKeyProvider`/`SymmetricKeyIssuerSecurityKeyProvider`, not the older `IIssuerSecurityTokenProvider` shape some older Katana samples show — that older shape doesn't exist in the package version this app resolves. After JWT validation, `PermissionService.CanExecuteAsync(userId, functionCode)` checks `dbo.SapDepartmentPermissions` (SQL Server) — a user passes if any of their `PortalUserDepartments` departments has a matching row for that function code, or a `*` wildcard row. Results are cached per-`(userId, functionCode)` for `Auth:PermissionCacheSeconds` (default 60) and the lookup **fails closed** — any SQL error denies access rather than allowing it.

Dev bypass: `Auth:DevBypassAuth=true` (Development environment only) swaps in `DevAuthMiddleware` + `NullPermissionService`, auto-authenticating every request. `DevAuthMiddleware` is a plain `OwinMiddleware` that sets `context.Authentication.User` directly — there's no ASP.NET-Core-style scheme registry to hook an alternate `AuthenticationHandler<T>` into under OWIN, so `Startup.cs` installs it *in place of* the JWT middleware entirely when the flag is set, rather than registering it as an alternate scheme. `Auth:BypassPermissions=true` still requires a valid JWT but skips the SQL permission check — use only until `SapDepartmentPermissions` is provisioned. Neither should be enabled in production.

### Background Services

`SapSessionMonitor` pings every **stateless pool** destination with `RFC_PING` every `HealthCheckIntervalSeconds` to prevent SAP's own idle-session timeout on a pooled RFC connection. Pinned/elevated sessions are deliberately excluded — they only exist for the duration of one active request (see "SAP NCo Connection Pool" above), so there is no idle window between health-check ticks for them to fall into. Ported off ASP.NET Core's `BackgroundService`/`IHostedService` (no generic host under OWIN/IIS) onto a plain `System.Threading.Timer` — `Start()`/`Stop()` are called explicitly from `Startup.ConfigurePipeline`, with `Stop()` wired to OWIN's `"host.OnAppDisposing"` cancellation token so the timer doesn't outlive an app-pool recycle.

### Error Handling

Two handlers, both mapping through the shared `SapExceptionMapper.Map(Exception)`, converge on the same JSON envelope:
```json
{ "success": false, "error": { "code": "ERROR_CODE", "message": "..." } }
```

- **`WebApiExceptionHandler`** (`System.Web.Http.ExceptionHandling.IExceptionHandler`, registered via `httpConfig.Services.Replace(...)` in `Startup.cs`) is what actually handles almost every real exception. Web API 2's `HttpServer` catches any exception raised during controller construction, filters, or action execution **itself** and converts it to a response *before* it can ever reach OWIN middleware above `UseWebApi` — so `SapPermissionException`/`SapConnectionException`/`SapExecutionException`/`PoolExhaustedException`, all thrown from inside a controller action or a helper it calls, only ever reach this handler, never `ExceptionHandlingMiddleware`. Discovered the hard way: without this, every one of those was silently replaced by Web API's own generic `{"Message":"An error has occurred."}` 500 — invisible until CI actually drove requests through the real `Microsoft.Owin.Testing.TestServer` pipeline (`RfcControllerTests`/`ProductionControllerTests`), since every other controller test uses direct Moq instantiation and never exercises Web API's real pipeline at all.
- **`ExceptionHandlingMiddleware`** (an `OwinMiddleware`) only ever sees an exception thrown *outside* Web API's pipeline entirely — e.g. from the CORS or JWT bearer middleware itself. Genuinely rare in practice, but kept as a backstop.

| Exception | HTTP | Code |
|---|---|---|
| `SapPermissionException` | 403 | `FORBIDDEN` |
| `SapConnectionException` | 503 | `SAP_UNAVAILABLE` |
| `SapExecutionException` | 422 | `RFC_ERROR` |
| `PoolExhaustedException` | 503 | `POOL_EXHAUSTED` |
| `OperationCanceledException` | 499 | `REQUEST_CANCELLED` |
| `UnauthorizedAccessException` | 401 | `UNAUTHORIZED` |
| (anything else) | 500 | `INTERNAL_ERROR` |

**`[Authorize(Roles = "...")]` returns 401, not 403, for an authenticated user with the wrong role.** Unlike ASP.NET Core's `[Authorize(Roles=...)]`, `System.Web.Http.AuthorizeAttribute.IsAuthorized` returns `false` for both "not authenticated" and "wrong role" alike, and `HandleUnauthorizedRequest` always maps that to 401 — Web API 2 has no built-in distinction between the two failure modes (confirmed against the real assembly via `RfcControllerTests.Status_requires_admin_or_superadmin_role`).

**Every controller action with an optional `[FromUri]` value-type parameter needs an explicit default** (e.g. `bool dryRun = false`), never a bare `[FromUri] bool dryRun`. Without one, Web API 2's real routing 404s the *entire request* — not just a bad-default value — whenever the caller omits that query parameter, which is the normal case for `dryRun` (real callers doing a real operation, not a dry run, don't pass `?dryRun=true`). This was completely invisible in this codebase until CI exercised real Web API routing, since every controller test that predates `RfcControllerTests`/`ProductionControllerTests` uses direct Moq instantiation and never goes through actual `[FromUri]` binding at all. `[FromUri]` parameters that are already nullable (`string?`, `int?`, a complex query-object type) don't need this — only non-nullable value types without a C# default do.

### Domain Helpers

`Helpers/` holds typed RFC/BAPI request builders and response parsers, one broadly per business area: `ProductionHelpers`, `PurchasingHelper`, `WarehouseHelpers`, `QualityHelpers`, `PackagingHelpers`, `CostingHelper`, `CustomsHelpers`, `LogisticsHelpers`, `ConsignmentHelpers`, `PerformanceHelpers`, `SalesHelpers`, `FunctionHelper`, `MrpAnalysisHelper` (goods-receipt-by-vendor history + the recursive `ExplodeBom` orchestration — see below), plus cross-cutting ones: `BdcBuilder` (BDC/session-based posting helpers), `RfcRequestBuilder`/`RfcRowHelpers` (generic request/table-row construction), `ReturnTableHelper` (parsing SAP's RETURN/BAPIRETURN messages), `GoodsReceiptHelper`, `StockAdjustmentHelper`, `ZdelflagHelpers`, `GoodsIssueHelper` (Goods Issue posting via BAPI_DELIVERYPROCESSING_EXEC, fired automatically by Normanton-Nexus right after ZDELFLAG maintenance succeeds — see GoodsIssueModels.cs for the caveat on its still-unconfirmed minimal REQUEST-table field set), `SapDelimitedParser` (WA/delimited raw-table parsing for `ZRFC_READ_TABLES`-style reads), `SapPad` (material-number/field zero-padding), `WhereClauseBuilder`, `CommitHelpers`. New SAP integrations should add a helper here rather than putting NCo dispatch code in a controller.

**This entire layer is transport-agnostic** — every builder produces a plain `RfcRequest` (a POCO with zero COM or NCo dependency) and every parser consumes a plain `RfcResponse`; `NcoRfcExecutor.Execute` is the only place that translates those POCOs into real NCo calls. That's why this layer needed essentially no changes for the NCo rebuild beyond the net48 BCL-gap fixes noted in "Testing" above — the Goods Issue, PO-price, and ZDELFLAG-parsing fixes that landed on `main` while this rebuild was in progress merged in cleanly for exactly that reason.

### MRP Analysis (`MrpAnalysisController`/`MrpAnalysisHelper`)

Backs Normanton-Nexus's MRP Analysis screen (year-on-year consumption/goods-receipt trends per material and vendor, plus two sales-forecast-to-raw-material methods).

- **Consumption-by-year** reuses `PerformanceHelpers.BuildConsumptionHistoryRequest` as-is (the same unfiltered-by-material MVER pull the daily TurnsValClass sync already makes, which already nets 6 fiscal years) — `PerformanceHelpers.ParseConsumptionHistoryByYear` is a second parser over the same response, summing `GSV01..GSV12` per `(Material, GJAHR)` instead of windowing into the rolling 36-month array `ParseConsumptionHistoryRows` produces. No new RFC call.
- **Goods-receipt-by-vendor history** is built on `MSEG`/`MKPF` (goods-receipt lines, movement 101) + `EKKO` (PO vendor), **not `EKBE`** — `EKBE` was the original plan but doesn't reliably carry `MATNR`, and `ConsignmentHelpers.BuildVendorGrRequest` already has a real, production-proven `MSEG`+`MKPF` goods-receipt pull in this codebase to build on instead of guessing at a new table cold. Filtering is deliberately single-value `EQ`/`GE` only (never `IN opt`) for this pull — see `ConsignmentHelpers.BuildVendorGrRequest`'s own header comment for the confirmed, real failure this RFC wrapper hit combining an `IN opt` condition with other WHERE conditions in one call (silently returned zero rows). MSEG-LIFNR is only populated by SAP for vendor-linked stock categories (consignment/subcontracting) — blank for an ordinary PO receipt, where `MrpAnalysisHelper.AggregateGoodsReceiptHistory` resolves the vendor via the PO's own EKKO-LIFNR instead, joined in memory.
- **`ExplodeBom`** recursively explodes a set of finished-good/quantity pairs down to raw materials (profit centre `0000002012`), one BOM depth per "wave": `ProductionHelpers.BuildBomRequestBulk` (bulk, `MATNR IN opt` variant of the existing single-material `BuildBomRequest`, mirroring `BuildProfitCentresRequest`'s proven `IN opt` shape) for that wave's components, then `BuildProfitCentresRequest`/`ParseProfitCentreRows` to classify them. Quantity multiplication (`parentQty * row.ComponentQty`) mirrors `ProductionController.PostScrap`'s existing, already-trusted-for-real-postings treatment of `BomRow.ComponentQty`. A BOM cycle or a branch still unresolved at the depth cap is folded into the raw-material totals (not silently dropped) but flagged in `BomExplosionResult.Unresolved`.
- **Unverified against a live SAP session** (no SAP GUI or NCo license in any environment this has been developed in — see "Migration Notes"): the `MSEG`/`MKPF`/`EKKO` goods-receipt pull's real-world retention/accuracy, and — highest stakes — whether `ExplodeBom`'s output matches a real, known multi-level BOM. Validate both before trusting the Sales Breakdown forecast method for an actual blanket PO.
- Permission: single function code `MrpAnalysisHelper.FnMrpAnalysis` (`"MRP_ANALYSIS"`) covers the whole controller (several endpoints call different underlying RFCs, same convention as `ProductionHelpers.FnCreate`) — needs a `dbo.SapDepartmentPermissions` row provisioned for the Logistics department; this repo has no migration file that manages that table (it's maintained out-of-band), so it's a manual one-time step, not something a future change here should expect to already exist.

## Migration Notes: ASP.NET Core + COM → .NET Framework 4.8 + NCo

This app was originally an ASP.NET Core 10 service wrapping the SAP GUI `SAPFunctions64` COM component (a 32-bit-to-64-bit-migrated OCX requiring an STA thread per session). A `Services/Nco/*` proof-of-concept later validated that SAP NCo could replace that COM dependency; this rebuild then replaced the *entire* stack — hosting model, DI, config, auth, and every controller — in one pass, on the premise that the specific SAP NCo package available only ships .NET Framework assemblies (not a .NET-Core-compatible build). If that premise turns out to be wrong for a newer NCo version, the far smaller change would have been keeping ASP.NET Core and only swapping the SAP transport — worth confirming before repeating a rebuild this size in the other direction.

What changed, mechanically:
- **Hosting**: Kestrel/generic-host → OWIN hosted in IIS (`Microsoft.Owin.Host.SystemWeb`). `Program.cs` → `Startup.cs` (`[assembly: OwinStartup(typeof(Startup))]`), `IApplicationBuilder`/`app.UseMiddleware<T>()` → `IAppBuilder`/`app.Use<T>()`.
- **DI**: still `Microsoft.Extensions.DependencyInjection` (targets netstandard2.0, works fine on net48) — a plain `ServiceCollection` is built and resolved manually in `Startup.cs`, bridged into Web API 2 via `ServiceProviderDependencyResolver : System.Web.Http.Dependencies.IDependencyResolver`.
- **Config**: still `Microsoft.Extensions.Configuration` (same netstandard2.0 story) — `appsettings.json` + `appsettings.{Environment}.json` + env vars, built explicitly in `Startup.BuildConfiguration()` instead of `WebApplicationBuilder.CreateBuilder(args)` doing it implicitly.
- **Auth**: ASP.NET Core JWT Bearer → Katana's `Microsoft.Owin.Security.Jwt`.
- **SAP transport**: `SAPFunctions64` COM/STA (`SapConnectionPool`/`SapStaWorker`, deleted) → SAP NCo (`NcoConnectionPool`/`NcoWorker`) — see "SAP NCo Connection Pool" above. `ISapConnectionPool`'s interface contract was kept **identical** on purpose, so all ~15 domain controllers needed no logic changes beyond the mechanical ASP.NET-Core-to-Web-API-2 port.
- **Tests**: `WebApplicationFactory<Program>` → `Microsoft.Owin.Testing.TestServer`.
- **Deploy**: Task Scheduler + self-contained win-x64 publish → IIS site/app pool + framework-dependent publish (see "Critical Platform Constraints").

**What is genuinely unverified**, roughly in order of real-world risk:
1. **`RfcSessionManager.BeginContext`/`EndContext`'s pinned-connection behavior** — the correctness of every transactional endpoint (anything using `AcquireWorker`/`AcquireElevatedWorkerAsync` + `ExecuteOnWorkerAsync`) depends on this working as documented. See "SAP NCo Connection Pool" above.
2. **Whether the SAP NCo package this app targets actually requires .NET Framework** — the premise this whole rebuild was built on; a newer NCo release may ship a .NET-Core-compatible build, which would make this rebuild's *scope* (not its SAP-transport work) unnecessary.
3. **Live SAP connectivity at all** — no SAP GUI, no NCo license, and no real `sapnco.dll`/`sapnco_utils.dll` exist in any environment this was developed against; `interop-stubs/SapNco.DevStub` is a compile-only stand-in written from memory of the public API (see that project for its own caveats).
4. **The whole OWIN/IIS hosting pipeline** — auth, CORS, routing, `web.config`, Swagger — has never run against a real IIS instance.
5. **Every test in `SapServer.Tests`** — compiles cleanly (0 errors) but has never executed (see "Testing" above).

## Key Configuration Keys

| Key | Purpose |
|-----|---------|
| `SapNco:MaxConcurrentPinnedSessions` / `ElevatedWorkerCount` | Concurrency caps for ephemeral pinned/elevated sessions, not thread counts (default 4 + 2) |
| `SapNco:PinnedAcquireTimeoutSeconds` / `ElevatedAcquireTimeoutSeconds` | Max wait for a free pinned/elevated slot before `PoolExhaustedException` (default 30 each) |
| `SapNco:MaxQueueDepth` | Per-pinned-session queued-item cap before rejecting new work on it (default 50) |
| `SapNco:HealthCheckIntervalSeconds` | How often the session monitor pings the stateless pool to keep it warm (default 60) |
| `SapNco:ReconnectDelayMs` | Backoff before the stateless pool's single retry after a connection failure |
| `SapNco:ServiceAccount.*` | SAP AppServerHost/SystemNumber/Client/User/Password/Language for pinned sessions and the stateless pool's fallback — NCo's own connection fields, not SAP GUI logon-pad concepts |
| `SapNco:ServiceAccounts` | Optional array of per-destination accounts for the stateless pool (destination *i* → `ServiceAccounts[i % Count]`, round-robined); falls back to the single `ServiceAccount` when empty |
| `SapNco:PoolSize` / `MaxPoolSize` | NCo's own internal RFC connection pool size per stateless-pool destination — the real concurrency knob for ordinary calls, independent of any thread count (default 10 / 20) |
| `Auth:JwtSecret` / `JwtIssuer` / `JwtAudience` | Shared HMAC-SHA256 secret + issuer/audience with sql2005-bridge/Normanton-Nexus |
| `Auth:SqlConnectionString` | DB for permission tables (`PortalUsers`, `PortalUserDepartments`, `SapDepartmentPermissions`) |
| `Auth:PermissionCacheSeconds` | Permission-check cache TTL (default 60) |
| `Auth:DevBypassAuth` / `BypassPermissions` | Dev-only auth/permission skips — never enable in production |
| `AllowedOrigins` | CORS origins for the frontend |
